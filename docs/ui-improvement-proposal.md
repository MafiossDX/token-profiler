# UI 改善提案: 調査から比較までの導線

- 作成日: 2026-09-06
- 状態: 提案。採用・実装は未決定。
- 評価範囲: spec の主要部分、主要 UI コンポーネント、診断ロジック、README、CONTEXT、関連 ADR。ブラウザでの見た目・操作感は未検証。

## 目的

token-profiler の価値を「使用量が分かる」から、「調べるべき request と根拠が分かり、設計変更の前後を確かめられる」へつなげる。

外部フィードバック「Token 観測ツールの今後の役割: Token Profiler から Agent Execution Profiler へ」と、現在の UI に対する評価を踏まえた改善案を記録する。外部フィードバックの原文はリポジトリ外にあり、本書には検討に必要な要点をまとめる。

本書は既存仕様や ADR を上書きしない。採用時には [UI 情報設計](ui-information-design.md) と必要な ADR を更新する。

## 取り入れたい方向性と維持する境界

外部フィードバックのうち、実行経路の理解と、同じ成果を目指す実行の比較を重視する方向に賛成する。総合的な Agent APM への拡張を、直ちに開発目標とするものではない。

- 重複していることは、不要・削減可能であることを意味しない。
- Context Amplification、provider が報告する token 数、cache、実行時間、成果を別の軸として扱う。
- 「Reviewer correction」のような用途と「Context duplication」のような性質は重なり得る。排他的な内訳として足し合わせない。
- Role や Phase は明示的な情報源がある場合に扱い、通信内容から用途を断定しない。
- 「スコープ外の作業だった」「変更すれば何 token 削減できた」という判断は、通信の観測だけでは確定しない。
- proxy が測る request-visible context と、provider 側に保持される effective context を区別する。
- 生本文を常時保存しない方針、観測値と診断の区別、合成スコアを作らない原則を維持する。

関連: [CONTEXT](../CONTEXT.md)、[ADR-0016](adr/0016-ui-leads-with-diagnostic-reading.md)。

## 1. 調査候補と根拠を近くに置く

### 現状の課題

サマリー、Next focus、グラフ、ランキング、request 表、タイムライン、詳細が縦に並ぶ。候補の選択から根拠の確認まで、画面内を上下に探す負担が生じる可能性がある。

### 改善案

- Task 概要の下に、調査一覧と選択 request の詳細を隣接配置する。
- ランキング・request 表・タイムラインの選択を、同じ request 詳細に連動させる。
- 狭い画面では詳細を選択箇所の近くに表示するなど、一覧に戻る位置を失わない構成を検討する。
- 一覧の選択状態、ソート、フィルタを更新時にも維持する。
- Next focus から該当 request や thread の調査へ直接進めるようにする。

### 確認したいこと

候補を選んだ後、詳細を探すスクロールなしで根拠を読めるか。候補を連続して切り替え、比較できるか。

## 2. 数値の意味と集計範囲を明確にする

### 現状の課題

大きな Amplification と `Critical` の表示は、再送倍率の高さを異常や無駄と受け取らせる可能性がある。thread 選択時に Task 全体の Amplification と thread 単位の token 数が同居する点も、読み違いにつながり得る。

### 改善案

- Task 概要に request 数、実行時間、観測 token 数、cache、Classification Coverage をコンパクトに併記する。未取得の値は不明として扱う。
- Task 全体の値と、選択 thread の値を表示領域で区別する。
- `Critical` などの評価語を「再送倍率 10 倍以上」のような記述的な表現へ変更する案を検討する。
- 「削減候補」を「重複量の大きい request」などに変更し、調査の優先順位であることを示す。
- 参照ゾーンを残す場合は、倍率自体の計測上の性質と、閾値が heuristic であることを分けて示す。

request 詳細の「この request を除くと CTV − UCV が減る」という表現も見直す。request を除外すると一意 context の集合や後続の再利用判定が変わり得るため、観測済みの重複量をそのまま反実仮想の削減効果に置き換えない。「この request で観測された重複量」として提示する。

### 確認したいこと

利用者が、数字の単位・集計範囲・観測できた範囲を判別できるか。高い倍率を、それだけで不具合や削減可能量と解釈しないか。

## 3. request 詳細に重複の手がかりを加える

### 現状の課題

順位、重複率、byte 数だけでは、「何が繰り返されたか」を掘り下げにくい。

### 改善案

fingerprint を用いた出現履歴を検討する。

- どの StructuralBlock / ContentChunk が繰り返されたか。
- 観測範囲内で最初に現れた request はどれか。
- 何件の request、どの thread で再登場したか。
- 対象の出現箇所へ移動し、前後の request を確認できるか。

Block Fingerprint と Exact Fingerprint は粒度が異なるため、ブロック全体の一致と部分的な chunk の再利用を混同しない。最初の出現は「観測範囲内での初出」であり、情報の生成元と断定しない。

### 実装前の確認

必要な関連付けが既存 DB に保存されているか、集計 API で返せるか、履歴の取得コストが許容できるかを確認する。既存データで実現できるとは未確認。本文を保存せずに有用な根拠を示せるか、小さな実例で検証する。

## 4. Task 比較を追加する

### 目的

Harness や運用ルールの変更後に、何が変わったかを確かめられるようにする。

### 最初の範囲

- 2 つの Task を選び、観測 token 数、実行時間、request 数、重複量、Amplification、cache を並べる。
- 成果の成否と変更条件は、利用者による明示入力など出典の分かる方法で扱う。プロセス終了だけで成功と判定しない。
- モデル、計測条件、Classification Coverage、観測方式の違いを見えるようにする。
- 値が取得できない場合や比較できない場合を、ゼロと区別する。
- 自動的な優劣判定や、単一の効率スコアは追加しない。

異なる tokenizer や server-side context の利用方式をまたぐ比較では、token 数や送信 byte 数の差だけを効率差と解釈しない。2 回の実行差から変更の因果効果を確定しない。

## 5. 日常利用の状態表示を整える

- Task に名前やメモを付け、ID だけに依存せず見分けられるようにする。
- 接続状態、最終取得成功時刻、更新停止を見えるようにする。
- 初回読み込み、取得失敗、空データ、記録済みデータの表示を区別する。
- ポーリング失敗時に前の値を保つ場合、その値が最新ではない可能性を示す。

名前やメモの永続化は新しい書き込み操作になる。採用時には、現在のローカルデータ管理方針と API の更新範囲を明示する。

## 推奨する実施順序

| 段階 | 対象 | 狙い |
|---|---|---|
| 1 | 調査一覧と詳細の連動、集計範囲・表現・取得状態の整理 | 既存データで調査しやすくし、誤読を減らす |
| 2 | fingerprint による出現履歴 | 数値から具体的な調査根拠へ進める |
| 3 | Task 比較と明示的な実行条件・成果の記録 | 設計変更の前後を検証できるようにする |

Task の名前・メモは、保存方針を決めたうえで段階 1 または 3 に組み込む。

グラフの種類を増やすことより、「候補を選ぶ → 根拠を読む → 変更前後を確かめる」という一連の操作を優先する。

## ドキュメントの補助的な改善

- 現在できること、未実装、既知の限界、正本へのリンクをまとめた短い現状ページを検討する。CONTEXT や ADR の履歴をすべて読まずに現状を把握できるようにする。
- README に、実際の観測で何を発見し、どの判断につながったかという実例を 1 件追加する。
- spec の MVP は範囲が広いため、現在の実装対象と将来構想を区別する。最初の到達点は「1 つの Task で調査対象と根拠が分かる」とする案を検討する。

## 検証の進め方

実 Task を使い、「重複量の大きい request を見つける」「その根拠を確認する」「別 Task と比較する」という操作を試す。調査にかかる時間、不要な画面移動、集計範囲や削減可能性の誤読が減るかを確認する。

実装前に UI の配置案を検証し、採用後に関連仕様を更新する。観測結果から一つの改善判断に到達した事例を残し、機能数ではなく調査の完遂を評価する。
