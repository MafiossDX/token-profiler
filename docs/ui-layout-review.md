# UI レビュー: request 一覧・表示順・Export

- 作成日: 2026-09-07
- 状態: **採用済み(ADR-0018)**。結論の 4 点(request 表のページング、5 と 7 の統合、表示順、Export の
  配置)を全面的に実装した。決定と理由は
  [ADR-0018](adr/0018-request-investigation-panel-and-pagination.md) に記録する。以下の本文(分析・
  推奨仕様)は提案時点のまま変更していない。
- 対象: 現在の作業ツリーの `src/ui` と [元の改善提案](ui-improvement-proposal.md)、[ADR-0017](adr/0017-ui-brings-evidence-adjacent-and-softens-labels.md)。未コミットの修正も含めて確認した。
- 確認方法: ソースレビュー。ブラウザでの操作検証・大量データでの性能測定は未実施。以下の表示件数や配置は、この UI の調査導線に基づく設計提案であり、実測による最適値ではない。

## 結論

| 論点 | 判断 | 推奨する変更 |
|---|---|---|
| 7 · request 表のページング | 必要 | 全件描画をやめ、件数表示付きのページングを導入する |
| 5 と 7 の重複 | 一覧部分の統合を推奨 | 7 を土台に、5 の重複量バー・占有率・集中度の要約を残す |
| 表示順 | 調査一覧を前に出す | 概要 → Next focus → request 調査と詳細 → 推移 → 内訳 |
| 8 · Export | 独立した末尾セクションを外す | 選択 Task の見出し付近に Export ボタンを置く |

情報量を減らすだけでなく、「候補を知る → 選ぶ → 根拠を読む」を短くすることを優先する。重複量は調査の手がかりであり、不要な文脈や削減可能量の判定ではない、という現在の方針は維持する。

## 1. request 表にはページングを入れる

### 現状と理由

[Requests.tsx](../src/ui/client/components/Requests.tsx) はフィルタ後の全件をソートし、[DataTable.tsx](../src/ui/client/components/DataTable.tsx) が全行を描画している。`.scrollx` は横スクロールのみで、縦方向の長さを制限していない。

件数が増えると、表の下部まで移動する負担に加え、行を選んだ後に表より上の Request detail に戻る負担が増える。ページングは性能問題が実測される前でも、一覧の長さと現在位置を管理するために価値がある。

### 推奨する初期仕様

- 初期は 20 件、選択肢は 20 / 50 / 100 件。「全件」は常設しない。
- 「41–60 / 238 件」、前へ・次へ、現在ページを表示する。操作は一覧の上下から行えるようにする。
- **フィルタ → 全対象のソート → ページ分割**の順に処理する。ページ内だけのソートにはしない。同値の並びは requestIndex で安定させる。
- Task・フィルタ・ソート・表示件数を変更したら先頭ページへ戻す。選択 request が対象内なら詳細の選択は維持し、「選択中の行へ」で戻れるようにする。
- Next focus やタイムラインから request を明示選択した場合は、対象行のページを開く。フィルタ外なら対象を表示できるスコープへ変更し、変更後のスコープを明示する。
- 自動更新ではページを先頭に戻さず、選択は requestIndex で保持する。順位変化で行が別ページへ移っても詳細を別 request に差し替えない。ページ数が減った場合は有効な最終ページに補正する。
- データなしとフィルタ結果 0 件を区別し、0 件ではページ送りを無効にする。
- CSV / JSONL の出力対象は、現在ページではなく、指定スコープの全 request と明示する。

まずはクライアント側のページングでよい。ただし、これは表の描画量と縦の長さへの対策である。[app.tsx](../src/ui/client/app.tsx) は 5 秒間隔で更新し、[server.ts](../src/ui/server.ts) は Task 全体の metrics を返すため、全件取得・集計の負荷は残る。大量データで問題が確認されたら、一覧 API のページングと全体集計の取得を分ける検討が必要になる。グラフの全件描画も別途測定対象とする。

## 2. 5 と 7 は一覧を統合する

「同じ request を重複量順で二度見る」という指摘に賛成する。ただし、完全に同一の情報ではない。

| 現在の表示 | 固有の価値 |
|---|---|
| 5 · 重複の多い request | 重複量の相対バー、gap 占有率、上位 K 件で全体の何割を占めるかという集中度 |
| 7 · request 表 | 重複 byte 数の数値、時刻、model、operation、入出力 token、cache、各種 byte 数、latency、多列ソート |

[ReductionCandidates.tsx](../src/ui/client/components/ReductionCandidates.tsx) は初期 20 件・50 件・全件の切替を持ち、7 の既定ソートも重複文脈 byte 数の降順である。候補探しの操作が重複しているうえ、5 と 7 のソートは独立している。

### 推奨案

**7 の全 request へのアクセスを残し、5 の独立したランキング一覧を廃止する。** 統合後の名称は「request 調査」とする。

- 既定は重複量の降順。重複量の数値と小さなバー、reuse 比、Task 全体の重複量に対する割合を表示する。
- 初期列は request 番号・thread・重複量・reuse 比・占有率程度に絞る。時刻や token、cache などの列は「詳細列」で表示できるようにし、複数行の数値比較も維持する。
- 集中度は「Task 全体では上位 K 件で重複量の 80%」という短い要約を一覧の上に残す。Pareto グラフは必要時に展開する。
- 集中度と占有率の分母を明記する。現実装の Pareto と gap% は Task 全体基準であり、thread フィルタ後の一覧に合わせて暗黙に分母を変えない。ページ内の合計も分母にしない。
- 重複量がゼロなら「重複文脈バイトは 0」と示し、「上位 K 件で 80%」という要約は出さない。
- ページング・ソート・選択状態をこの一覧に一本化する。

Next focus は残してよい。最大 request だけでなく thread と閾値到達位置への入口もあり、「短い要約」と「全件を調べる一覧」では役割が異なる。ただしカードを増やして第二のランキングにしない。

## 3. 推奨する表示順

### 本命案: 調査操作を一つの領域にまとめる

| 新しい順序 | 表示 | 現在との対応・理由 |
|---|---|---|
| 上部の操作 | 選択 Task・フィルタ・Export | 対象範囲と操作を確認する。分析セクションの番号は付けない |
| 1 | Current amplification / Task 概要 | 現在の 1。規模・観測範囲・usage・coverage を最初に把握する |
| 2 | Next focus | 現在の 2。最初に調べる対象を知る |
| 3 | request 調査 ＋ Request detail | 現在の 5 と 7 を統合。現在の 6 のタイムラインは同じ調査領域内の表示切替として残す |
| 4 | 推移・閾値プロット | 現在の 3。調査対象が全体の推移のどこに位置するかを見る |
| 5 | 重複文脈バイトの内訳 | 現在の 4。thread や context class などの集計から掘り下げる |

目的が「最初に調べる request と根拠を見つける」であるため、候補と詳細を二つの集計グラフより前に置く。推移や内訳は削除せず、全体像から掘り下げたい場合も利用できるようにする。

調査領域は「一覧 / タイムライン」を切り替え、どちらから選んでも共通の Request detail を更新する。タイムラインの minimap / thread lanes はその中に残す。表示を切り替えても選択・ソート・ページ位置を維持する。

広い画面では一覧またはタイムラインと詳細を隣接配置する。狭い画面では選択行の直後に詳細を展開するなど、選んだ場所で読める構成を検討する。タイムラインでは図の直下に出す。ページ全体に追従する sticky サイドバーは不要。

現状の [Detail.tsx](../src/ui/client/components/Detail.tsx) はタイムラインと詳細だけを横並びにしている。5 はその前、7 はその後なので、**順序を入れ替えるだけでは、長い一覧の途中から詳細を読む距離は解消しない**。一覧と詳細の隣接を、ページングと合わせて扱う必要がある。

### 統合を後回しにする場合の暫定順

既存パネルを残した配置変更だけなら、**1 → 2 → 5 → 6（詳細を含む）→ 3 → 4 → 7** とする。Export は上部へ移す。

ただし 5 は上位 5〜10 件程度の短い要約に限定し、「すべての request を見る」で 7 に進める。5 の「全件」はなくす。この案は段階的な変更には向くが、一覧が二つ存在するため本命案より操作の重複が残る。

## 4. Export は Task の操作として配置する

Export は分析結果の一種ではなく、閲覧中のデータに対する操作である。ページ最下部の独立パネルより、**選択 Task の見出し右側に「Export」ボタン**を置き、クリックで形式と対象範囲を選べる配置を推奨する。狭い画面では同じ見出しの次の行に置く。

メニューには現在の [ExportPanel.tsx](../src/ui/client/components/ExportPanel.tsx) の機能を引き継ぐ。

- 「Task 全体」と「選択 thread」を明確に分け、metrics JSON / requests CSV・JSONL / threads CSV / blocks CSV を選べるようにする。
- context_class 選択時は、その属性で絞れるのは blocks CSV だけと示す。requests / threads が絞られるような表示にはしない。
- thread 指定の metrics JSON も scalar は Task 全体という現在の意味を説明する。「全数値が thread に限定される」と読めるラベルは避ける。
- 出力形式ごとの対象説明を保ち、単なるファイル名の羅列にしない。

統合 request 一覧のツールバーには「CSV 出力」のショートカットを残してよい。上部は Task 全体の出力窓口、一覧は対象 request を出す近道なので、こちらの重複は操作距離を短くする意味がある。「全 238 件を出力」のように対象件数を示し、ページングと混同させない。

## 5. 改修する場合の優先度と確認事項

1. **最優先: request 一覧の統合・ページング・詳細の隣接。** 表の長さと調査導線をまとめて改善する。
2. **次: 表示順の整理。** 概要と Next focus の直後から調査を始められるようにする。
3. **次: Export の上部移動。** 単独でも実施しやすい小さな改善として先行してよい。

採用後は、配置を定める [UI 情報設計](ui-information-design.md) と関連 ADR・仕様・UI テストを更新する。本書だけで既存決定を置き換えない。

実装時には次を確認する。

- 0 / 1 / 20 / 21 / 1,000 件で、全 request に到達でき、ページ境界に欠落・重複がない。
- 別ページの request を Next focus / タイムラインから選ぶと、その行と詳細に到達できる。
- ポーリングで件数・順位が変わっても、意図せず先頭ページや別の詳細に切り替わらない。
- thread / context_class のスコープと占有率・集中度・Export の対象が矛盾しない。
- 狭い画面とキーボード操作で、行選択 → 詳細確認 → 一覧に戻る操作を迷わず行える。
- ページング後も出力は指定スコープの全件となり、現在ページだけに限定されない。

大量データの描画時間・取得時間と、実際の調査操作に要するスクロール量を確認し、初期件数や列数を調整する。
